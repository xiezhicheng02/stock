# 指数基金估值定投系统

抓取 A 股宽基指数的估值数据，多指标加权生成综合评分，按估值高低给出**定投动作建议**
（大额买入 → 分批卖出），通过 HTML 邮件定时推送，并提供一个 Web 界面查看行情、
指标、评分与定时任务。数据源为 **baostock**，本地用 **SQLite** 全量落库，
设计用于在 **树莓派 3B+** 上长期常驻。

## 功能特性

- **数据源**：baostock（日 K 线 / 成分股 / 分红 / 交易日历），一次落库、离线复用。
- **五指标估值**：PE-TTM / PB / PS-TTM / PCF / 动态股息率。
- **指数估值聚合**：按成分股**流通市值加权**，PE/PB/PS/PCF 调和加权、股息率算术加权。
- **综合评分**：各指标对自身历史的**滚动分位**（10 年主口径 + 5 年参考口径），按权重合成 0~100 分（越高越贵）。
- **五档信号**：低估🟢大额买入 / 偏低🔵正常定投 / 正常⚪小额定投 / 偏高🟠停止定投 / 高估🔴分批卖出。
- **通知分级**：普通日每天一封；进入低估/高估告警态时一天最多 4 封。
- **Web 界面**：首页总览 / 标的信息 / 指数与组合 / 个股管理 / 设置，图表用 ECharts（前端本地打包，无外网依赖）。
- **定时任务**：拉取数据、计算指标、通知三套任务，由 APScheduler 与 Web 同进程运行。

## 架构总览

```
baostock（网络）
   │  拉取数据（定时任务 / 手动按钮）
   ▼
SQLite 数据库（data/stock.db，WAL 模式）
   │  计算指标（定时任务，纯离线）
   ▼
kline（估值绝对值） + valuation_score（评分/分位）
   │  通知（定时任务，读评分）
   ▼
HTML 邮件（可选预览 HTML）

Web 界面（FastAPI + ECharts，读库展示）
```

- **取数**：`src/fetch_data/data_fetcher.py`，只负责从 baostock 拉数据写入数据库。
- **计算**：`src/indicators/indicators.py`，只负责从数据库读数据、算指标/评分写回数据库。
- **编排**：`src/notify/pipeline.py`，把取数与计算串起来，供定时任务与手动按钮调用。
- **定时**：`src/web/scheduler.py` + `src/web/jobs.py`（APScheduler）。
- **展示**：`src/web/app.py` + `src/web/routers/*` + `src/web/static/*`。

## 快速开始

### 1. 环境要求

- Python 3.12
- 能访问外网（数据源 baostock）
- （树莓派）Raspberry Pi OS，可访问 `piwheels.org` 加速 ARM 预编译包

### 2. 安装依赖

```bash
cd stock
python3 -m venv .venv
source .venv/bin/activate

# 树莓派上用 piwheels 加速（省去现场编译）
pip install -r requirements.txt \
    -i https://www.piwheels.org/simple \
    --extra-index-url https://pypi.tuna.tsinghua.edu.cn/simple
```

### 3. 初始化数据库

```bash
.venv/bin/python script/init_db.py
```

这一步会创建全部表结构、写入默认配置（`setting` 表）和默认估值目标（`valuation_target` 表：
沪深300、中证500、科创50 组合）。

> **只执行一次**：`init_db.py` 检测到库已初始化过（`schema_version` 有记录）就会提示并退出。
> 之后的表结构升级与配置增删由服务启动时自动完成（`storage.ensure_schema()` +
> `config.ensure_settings()`），日常**不需要**再跑这个脚本。
> 确需把配置与估值目标恢复为出厂默认值时，显式加 `--force`。

> 敏感配置（SMTP 账号/授权码/收件人）在「设置」页的「邮件配置」里填写，不再需要
> `local_config.py`。`init_db.py` 会优先读取本地 `local_config.py`（若存在）作为初始值。

### 4. 启动服务

```bash
./script/run_web.sh              # 后台启动（日志 logs/web_<日期>.log）
./script/run_web.sh -f           # 前台启动（调试，Ctrl+C 停止）
./script/run_web.sh status       # 查看运行状态
./script/run_web.sh stop         # 停止
```

默认访问地址 `http://<主机IP>:8000/`（`WEB_HOST` / `WEB_PORT` 可在设置页改）。

### 5. 首次拉数

打开「指数与组合」或「个股管理」，点对应目标的「拉取数据」按钮，或直接用命令行全量拉取：

```bash
.venv/bin/python -m src.fetch_data.data_fetcher --full
```

首次全量拉取 800 只成分股历史 K 线（默认从 1990 年 A 股起点拉全历史）约需 1~2 小时，
增量任务之后会自动续传。

## Web 界面

| 页面 | 说明 |
|---|---|
| **首页** | 上证指数行情 + 数据统计 + **告警状态（可点击进标的详情）** + **邮件记录（可点击预览正文）** + **定时任务**（含执行状态、手动触发、最近执行记录）+ 运维按钮 |
| **标的信息** | 只读展示各估值目标：指标卡、K线、评分走势、五指标分位走势、权重 |
| **指数与组合** | 管理指数/组合：权重置顶、K线+评分+分位图、成分股增删、拉取数据、立即计算评分 |
| **个股管理** | 搜索/列出个股，查看详情，单只拉取数据 |
| **设置** | 分组编辑全部配置（邮件/定时任务/信号/权重/数据源/系统） |

首页的**上证指数**区域：

* 顶部是**行情横幅**（涨红跌绿浅底）：左侧名称 + 随涨跌变色的圆点 + 代码/日期/交易日数 +
  5/20/60 日涨跌组；右侧 34px 大价格 + 涨跌额胶囊 + 涨跌幅 + 昨收；
* 下方 **6 格行情快照**（今开 / 最高 / 最低 / 昨收 / 成交额 / 成交量），每格
  「标签 / 值 / 相对昨收的差额」三层，差额按红绿着色（与"基本信息"区同一套视觉语言）；
* 再下面是 K 线走势，带小节标题与右对齐的「近1月 / 近1年 / 全部」切换。

首页只有**一个「✉️ 邮件记录」卡片**，直接就是邮件列表——没有"最近发送"之类的概览块，
也没有单独的告警区域（告警只是邮件的一种状态）：

* 标题右侧两个徽章：今天这一封的推送进度（未构建 / **已构建·待发送** / 已发 N/4 次）
  + 当前告警标的数（`🔔 N 个告警标的`，悬停看是哪几个）；
* 列表列：时间 / 类型 / **标题 + 内容摘要** / 状态 / 收件人 / 操作。
  类型列用 `🔔 告警` 标出告警邮件，摘要列直接显示各标的状态与评分
  （例如「沪深300 便宜 48分；中证500 便宜 49分」），告警那一行左侧还有橙色提示条；
* **点任意一行或"查看正文"按钮，新窗口打开那封邮件的正文原件**；
  没有正文快照的历史邮件会打开一段说明页（功能上线前发出的邮件不存正文）。

> **点「生成邮件正文」后立刻就能在邮件列表里看到它**：那一行以蓝色「待发送」排在最上面
> （来自 `pending_alert` + `mail_body`，还没发出去但正文已经能预览）。
> 触发后页面会轮询任务状态，**这个任务一跑完就自动整体刷新**。

**定时任务的「执行」按钮**：调度器未运行时按钮不可点（悬停有提示）；运行中显示
"运行中…"并禁用（该行淡蓝底）；每次执行的结果都会进入"最近执行记录"。

定时任务表格用 `table-layout: fixed` + `colgroup` 固定列宽
（任务 17% / 触发时间 18% / 下次运行 17% / **执行状态 36%** / 操作 12%）：
执行状态列空间最充裕，它下面可能很长的执行摘要限两行、超出省略（悬停看全文），
不会把其它列挤变形。

> **手动点「执行」= 明确意图，会绕过"非交易日跳过"**。定时执行时
> `SKIP_NON_TRADING_DAY=True` 且当天休市 → 构建任务会跳过（这是对的，休市数据没变）；
> 但周末你想生成一份预览时，手动执行会强制构建。**「生成邮件正文」执行前会先把
> 标的信息补算到最新**（股息率/指数估值/组合K线/综合评分，幂等，没事时几乎不耗时），
> 保证邮件内容和库里一致；补算正忙时用现有数据生成并在结果里说明。
>
> **「发送邮件」按钮的语义是"现在就发一封"**：如果当天还没构建正文，它会**先构建再发送**
> （否则点了会因为"还没到构建时间"而空转）；当天已经发过一次则跳过（`sent_count > 0`）。
> **「告警重发」按钮只有在当天那封邮件确实是告警时才发**——不是告警就直接跳过
> （结果写「跳过重发：非告警邮件，无需重发」），不会凭空造一封邮件出来。
>
> 当天没构建成功时，邮件卡片会直接写出**构建任务的原因**
> （例如「最近一次构建：跳过构建：今天不是交易日」），不会只留一片空白。
>
> **重复构建不会导致重复发信**：正文会被最新数据替换，但 `pending_alert.sent_count`
> 保留不动，所以"今天已经发过几次"这件事不会被抹掉。
>
> 顶栏原来那个「刷新」按钮已去掉——顶栏状态本身每隔 `WEB_HEALTH_REFRESH_SEC`
> （默认 **300 秒**）自动刷新一次 `/api/health`，
> 各页面也都有自己的刷新入口。
>
> 这个间隔**只决定顶栏那行状态文字多久更新一次**，所以默认给得比较长：
> 它曾经叫 `WEB_PAGE_REFRESH_SEC`、默认 30 秒，名字像是"页面刷新"、实际却只是
> 在轮询健康检查（页面数据并不跟着刷新），既容易误解又是没必要的 30 秒一次轮询。
> 现在正名为 `WEB_HEALTH_REFRESH_SEC` 并降到 300 秒；旧键已进墓碑清单，
> 老库启动时会被自动清掉（改动需重启服务 + 页面强制刷新）。

### 标的信息 = 估值目标（决定"算谁、发什么"）

`valuation_target` 表就是「标的信息」：**个股管理 / 指数与组合 / 标的信息**三页的详情里，
右上角「指标与权重」卡片可以把自己**添加为标的信息**——填五个指标的评分权重即可：

* 添加后它出现在「标的信息」页，并参与评分与邮件构建
* **邮件正文、发送内容完全基于标的信息**（`report.collect` 只取 `config.targets()`）
* 已加入的可以「修改权重」，或「移出标的信息」（会一并清掉成分股与评分；
  组合还会删掉自己合成的 K 线）

**顺序可以调，邮件顺序跟着走**：左侧列表每行的 ▲▼ 调的是**全局顺序**
（`valuation_target.sort_order`，`PUT /api/target-order` 一次提交完整 codes 顺序）。
这个顺序 = 左侧列表的展示顺序 = **邮件里各标的的先后**（`report.collect` 按
`sort_order` 排），所以排好之后发出去的邮件顺序与界面完全一致。

> 列表是**平铺**的（不按指数/组合/个股分组），因为顺序是全局的：分组显示会出现
> "点了 ▼、邮件顺序真的变了，但界面上看不出变化"。类型改为每行右侧一个小标签
> （指数/组合/个股），这样 ▲▼ 点一下就能看到位置变化。

标的详情页（个股 / 指数与组合 / 标的信息）统一布局：顶部横幅（**名称 + 状态·操作建议胶囊**，
右侧综合评分 + 较前日）→ 基本信息 → 评分权重 → 五指标卡 → K线 / 综合评分 / 五指标分位走势。

顶部横幅的标题行是 `标的名称` + 紧跟其后的状态胶囊，例如
`沪深300 ［🤏 正常 · 小额/持有］`：胶囊底色/字色来自 `STATUS_STYLE`、图标来自
`ACTION_ICON`、短动作来自 `ACTION_SHORT`，处于 `ALERT_STATUSES` 时后缀 `ALERT_MARK`。
横幅右侧的**综合评分较前日变化**按方向配色：上升红（`--dear`）、下降绿（`--cheap`）、
持平灰，白底 + 方向色文字（横幅是评分色阶，白底才看得清），
评分越高越贵，所以涨用红、跌用绿，与全站涨跌一致。

胶囊字号是标题的 **0.6 倍**（20px → 12px），与标题垂直居中。
配色是**半透明白底 + 状态色文字**：横幅底色是评分色阶（绿→红），直接用
`STATUS_STYLE` 的底色经常和它撞色（实测对比度低到 1.01，几乎看不见），
白底保证任何横幅底色下都清楚，状态色仍作为文字色保留。名称过长或窄屏时胶囊自动换行。

**「指标与权重」是一张合并卡片**：权重堆叠条 + 图例 + 五张指标卡（彩色标签、
权重占比小标、当前值、10年分位）都在同一张卡里，不再分成两块。

**K 线图**会画一条**最新收盘价横线**（涨红跌绿虚线），并在 y 轴一侧用同色小胶囊
标出该价位的具体数值。

基本信息区固定为 **2 行 × 5 列** 的键值网格（每格「标签 / 数值 / 补充说明」三层，
缺值填 `—` 占位，所以两行永远等高对齐、不会因某只标的没有行业或成分股而塌格）：

| | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| **第一行**<br>标的属性 | 代码 | 类型<br><small>300 只成分股</small> | 市场 | 行业 | 上市日期 |
| **第二行**<br>最新数据 | 最新收盘<br><small>涨跌幅</small> | 综合评分<br><small>5年口径</small> | 评分权重<br><small>合计 %</small> | 分位偏离<br><small>阈值</small> | K线区间<br><small>行数</small> |

配色：涨跌幅**红涨绿跌**；综合评分用当前区间的颜色（`STATUS_STYLE`）；
评分权重**已配置=浅绿底 / 未配置=浅橙底+橙字**；分位偏离超过 `DIVERGENCE_THRESHOLD`
时橙色高亮；缺值统一浅灰。窄于 860px 才退成 3 列 / 2 列。

> 状态信息不在这里重复展示，只在顶部横幅的状态胶囊上出现。

### 邮件正文与网页「标的信息」页保持一致

**每个标的 = 一张完整的大卡片**（横幅 + 基本信息 + 指标与权重 + 全部图表都在这一张卡里，
卡片之间留 20px）。一封邮件里有多个标的时，靠这张卡片的边框把"这一块是一只标的"
圈出来，一眼就能区分；卡片内部用**浅底小面板**再分组（基本信息 / 指标与权重），
层次清楚但不像多张独立卡片那样吃掉纵向空间。图表之间只留约 34px
（旧版每张图各自一张卡是 78px）。

邮件按**与网页相同的区块顺序和卡片划分**渲染，每个标的一组卡片：

| 区块 | 邮件 | 网页 |
|---|---|---|
| 头部横幅 | 大卡片的**顶部整条色带**（不再是独立圆角块）：名称 + 紧跟其后的状态胶囊（白底/状态色文字/图标/短动作/⚡），下一行副信息（代码·类型·成分股·行业·上市）；右侧综合评分 + 较前日变化 | **一致**（无底部动作条） |
| 基本信息 | **2 行 × 5 列**：代码/类型/市场/行业/上市日期；最新收盘+涨跌/综合评分+5年/评分权重/分位偏离/K线区间 | 同 |
| 评分权重 | 堆叠条 + 图例 + 合计 | 同 |
| 指标与权重 | **合并成一张卡**：权重堆叠条 + 图例 + 五张指标卡（标签/权重小标/当前值/10年分位） | 同 |
| 图表 | **K线走势 → 综合评分走势 → 5 张单指标分位走势**（共 7 张 PNG，图间距约 34px）；**图内不画标题**，标题由 HTML 渲染成「标题文字 + 右侧小标签」（与网页 `.card-title` + `.ct-vals` 一致）；K 线同样画最新收盘价横线并只在**左侧** y 轴标值 | 同（网页是 ECharts 交互图） |

## 定时任务

三套核心任务（触发时间均可在「设置 → 定时任务」里改）：

> **是否执行由 baostock 股市日历决定**，不再用"星期范围"配置：
> 触发器是"每天"，任务开头查一次 `trade_date`（从 baostock `query_trade_dates` 同步），
> 非交易日直接跳过。这样能正确处理 A 股的**周末调休交易日**（按 mon-fri 会漏掉），
> 也不会在国庆/春节连休里空跑。开关是 `SKIP_NON_TRADING_DAY`（默认开，
> 关掉就每天都跑）；**手动点「执行」会强制跑**，不受日历限制。
> 日历里没有当天记录（未知）时不拦，正常执行——宁可多跑一次也不漏。

| 任务 | 触发 | 职责 |
|---|---|---|
| **拉取数据** `data_sync` | 每天 `SYNC_RUN_TIME`（默认 18:00，工作日） | 纯取数：K线(前复权+不复权收盘价)/成分股/分红/交易日历落库 + **K线完整性体检与补齐**，**不做计算** |
| **计算指标** `compute_indicators` | 每小时 **05 / 35 分**（按 `INDICATORS_INTERVAL_MINUTES` 生成固定分钟点，**每天都跑**） | 离线检查**所有个股/指数/组合**的分位，缺什么补什么（分阶段 + 并发），全部落库 |
| **通知** `notify` | 构建 03:00 → 发送 08:30 → 告警重发 11:30/18:00/21:00 | **只读库渲染**邮件正文（暂存 7 天）→ 发送 → 告警时最多重发（合计 4 次），**不计算、不取数** |

#### 三层的职责边界

```
data_fetcher（取数）: 只联网落库              —— 不 import indicators
indicators  （计算）: 只读库算、写库          —— 不 import data_fetcher
notify      （通知）: 只读库渲染 + 发信       —— 不算、不取
```

**这个边界是靠"不互相 import"来保证的**：`data_fetcher.py` 只 import `config`/`storage`，
`indicators.py` 里出现 `data_fetcher` 只存在于注释。所以「拉取数据」任务永远不会顺手算分，
「计算指标」任务也永远不会偷偷联网。

**手动入口在 `pipeline` 里编排**（同一个函数里先取数、再计算），但调用的仍然是上面三层
各自的纯函数：

| 手动操作 | 取数 | 计算 |
|---|---|---|
| 拉取单只标的 `pipeline.sync_target` | `data_fetcher.sync_target_data` | `indicators.compute_target` |
| 重算组合 `pipeline.rebuild_portfolio` | `data_fetcher.sync_constituents_data` | `indicators.fill_dividend_yields` + `rebuild_portfolio` |
| 一键跑批 `pipeline.run` | `sync_all` | `indicators.compute_all` |

> **通知任务不做补算**：早期版本 `build_notification` 会在构建前调一次
> `compute_indicators`（"保证邮件和库一致"）。但那与 30 分钟一次的「计算指标」
> 完全重复（实测每次白跑 15~60s），已去掉 —— 现在构建只花 ~12s（纯渲染 28 张图）。
> 代价是：如果「计算指标」任务挂了，邮件会用库里的旧数据构建（不会报错）。

#### 「拉取数据」的第 ⑦ 步：前复权历史修正（失败会记待办）

K 线**全部是前复权**（`ADJUST_KLINE = "2"`，写死的常量，**不是配置项** ——
早期的 `BAOSTOCK_ADJUSTFLAG` 开关已彻底移除，连墓碑清单里的清理项也删了）。
前复权价是"以最新价为基准往后倒推"算的，
所以**一旦发生新的分红送股，整条历史的价格都会变** —— 这决定了维护方式：

| 机制 | 作用 |
|---|---|
| `KLINE_OVERLAP_DAYS = 10` | 每次增量重叠重拉最近 10 天（修正盘中快照 + 近端除权） |
| 第 ⑦ 步：**发现新分红 → 该股全历史重拉** | 修正整条前复权历史 |
| `kline_readjust` 待办标记 | **重拉失败时不静默丢失** |

**为什么必须有那个待办标记**：新分红触发重拉时，分红记录**已经落库**了，
下一轮 `sync_dividends` 不会再报"新分红" → 重拉再也不会被触发。
一旦这次失败，那只股票的历史就**混着两套复权基准**（旧的一段 + 新的一段），
不报任何错、也不在缺口统计里，只在跨除权日的地方表现为一个不易察觉的小台阶。

所以第 ⑦ 步每次都同时处理「本次新分红」+「上次失败留下的待办」，
成功清标记、失败记标记（下次重试）。实测：失败后标记保留 ✅、成功后清除 ✅、
没有待办时不会无谓重拉 ✅（`refetch_for_readjust` 返回真实成败数）。

> 全量重拉时 `close_raw` 会被 UPSERT 的 `COALESCE` 保住（实测 5679 → 5679 行），
> 新增的历史日期再补一次 `sync_raw_close(full=True)`。

#### 元数据（名称/行业/上市日期/市场）为什么曾经长期缺失

`sync_all` 第 ③ 步用 `sync_stock_basics` 补全 `industry` / `listed_date`，
但**第 ④ 步的 `sync_constituents` 又把它抹掉了**：

```python
# sync_constituents 里：每次拉取都把**所有成分股**upsert 进 stock_basic
storage.upsert_stock_basic(conn, [
    {"code": c["code"], "name": c["name"], "ktype": "stock",
     "market": c["code"].split(".")[0]} for c in cons])   # ← 只带 4 个字段
```

而 `upsert_stock_basic` 当时是 `INSERT OR REPLACE`（先 DELETE 再 INSERT，
没出现的列会被抹成 NULL）→ 于是**每跑一次拉取，刚补好的 `industry`/`listed_date`
就被清空一次**（成分股几百只）。表现就是：覆盖率永远停在个位数百分比
（实测 852 只里只有 51 只有），而「个股信息」页的**上市日期、行业**一直是空白。

修法是把 `upsert_stock_basic` 也改成 UPSERT + `COALESCE`（新值为 NULL 时保留原值），
和 `upsert_kline` 保住 `close_raw` 是同一个套路。同时：

* `update_stock_basic_info` 改为**按批提交** —— 原来全部更新完才 commit 一次，
  中途失败会把已写成功的部分**全部回滚**；
* 第 ③ 步补完后**校验覆盖率**（`meta_coverage`），缺就写进同步摘要的 `skipped`，
  不再只留一行 warning 悄悄过去。

> 实测：修复后 6.0% → **99.9%**（856 只只剩 1 只 —— `bj.920599`，
> baostock 不覆盖北交所代码，连名称都拿不到，属正常）。

#### 「拉取数据」的第 ⑧ 步：K 线完整性体检与补齐

对每只个股检查：在 `[max(上市日期, BAOSTOCK_START_DATE), 最新交易日]` 内，
**交易日历里该有的交易日是否都有 K 线行**；缺了就全历史重拉那一只。

**为什么这个判据可靠**：停牌日 baostock **也会返回 K 线行**（`volume=0`，实测占 2.43%），
所以"某个交易日没有行"就一定是真缺数据，可以放心补 —— 不会像 `close_raw` / `div_yield`
那样出现"永远补不上、每天重试"的死循环。实测全库 838 只比对只要 **~0.9s**，每次拉取都跑。

**两个必须小心的坑**（都已处理）：

1. **终点不能被日历里的未来日期带偏**：日历含到明年年底的未来交易日，
   直接取 `MAX(date)` 会把 10~12 月还没到的日子也算成"该有 K 线"，导致每只股票
   都被误判缺一大截。所以终点取 `latest_trade_date(on_or_before=今天)`。
2. **上市日期未知时不能拿 `BAOSTOCK_START_DATE` 顶替**：一只 1995 年上市、
   库里有 2015 年起数据的股票会被算成缺 6000 个交易日，然后被当成"头部截断"
   去全历史重拉 —— 800 只一起跑就是几小时白工。所以上市日期缺失时**只检查
   中间/尾部缺口，不判断头部**，并记一条 warning。

**两个前置数据**（第 ⑧ 步依赖它们，都在同一次 `sync_all` 里更早的阶段补齐）：

* **交易日历要覆盖到 `BAOSTOCK_START_DATE`**：`sync_trade_dates` 的增量是从
  "库里已有日历的最新年份"往后接的、**从不回头**，所以建库时 start_date 若是 2015，
  之后改成 1990 也永远不会补 → 新增 `ensure_trade_calendar_span` 检测并整段重拉；
* **`stock_basic.listed_date` 要齐**：缺了就没法判断头部 → `sync_stock_basics`
  （已在第 ③ 步）负责，一次批量查询能补全。

**补齐过的打 `kline_full` 水位标记**（`sync_state.dtype='kline_full'`），
之后不再重复重拉 —— 否则那些"baostock 那边也没有"的缺口会每天触发一次全量重拉。

> 实测（接上 `close_raw` 修复那一轮）：初次体检识别出 **166 只**不完整
> （**165 只头部被截断** + **1 只中间缺口**），合计缺 26.7 万个交易日。
> 头部截断的根因和 `close_raw` 是同一个：建库时 `BAOSTOCK_START_DATE=2015`，
> 后来改成 1990，但增量逻辑只看尾部水位、**永不回头**。
> 例：`sz.000878` 缺 `2014-12-09 ~ 2014-12-31` 连续 17 个交易日（前后都有数据）——
> 这种中间缺口，只看尾部是否最新的老逻辑永远发现不了。


首页「定时任务」卡片可看到每个任务的**执行状态**（运行中/成功/失败 + 结果摘要），并可**手动触发**，
触发后页面自动轮询直到任务完成。

> **「跳过」不会覆盖「最近一次执行结果」**：被 `max_instances` 挡掉（上一次还没跑完）
> 和错过触发时间的事件，只进"最近执行记录"列表，**不写**该任务的 last 结果。
> 否则会出现"任务明明跑完了、界面上却显示失败"——例如 20:00 的 `data_sync` 还在跑，
> 20:21 有人手动点了一次被挡掉，那条"跳过"就把成功记录顶掉了（真实发生过）。
>
> **交易日守卫统一放在 `web/jobs.py`**（`pipeline` 内部不再判断），
> 这样"哪个任务什么时候跳过"只有一处；`build_notification` 只负责渲染。
>
> **「计算指标」故意不做交易日判断**（在 `jobs.NO_HOLIDAY_GUARD` 里）：它是纯离线
> 任务（只读库 → 算 → 写回，不联网），"库里有没有没算的"本身就是完备判据 ——
> 交易日守卫在这里是多余的，反而会让**周末/假期积压的补算一直拖到下一个交易日**
> （例如周五盘后补齐失败，要等到周一才自愈）。数据没变时数据闸门会在 0.3ms 内早退，
> 所以休市日跑也几乎不花代价。页面文案也据此**不加**"（仅交易日执行）"后缀，
> 避免显示与实际行为不一致。
>
> **计算任务的触发时刻是固定的分钟点**（每小时 05、35 分），不是 `interval` 触发器：
> interval 从**进程启动时刻**起算，`:00`/`:30` 启动就会让计算任务正好撞上 03:00 的
> 「构建正文」和 08:30 的「发送邮件」（两个任务同时读写 `valuation_score`）。
> 改成固定分钟点后永远避开，也不会因为重启而漂移。

**在「设置」页改这些定时任务配置，保存后立即生效，不用重启服务**：

| 设置节 | 配置键 | 作用 |
|---|---|---|
| 定时任务 · 拉取数据 | `SYNC_RUN_TIME` | 拉取数据任务的触发时间（是否执行看股市日历） |
| 定时任务 · 计算指标 | `INDICATORS_INTERVAL_MINUTES` | 计算指标任务的间隔（分钟） |
| 定时任务 · 通知推送 | `NOTIFY_BUILD_TIME`、`NOTIFY_SEND_TIME`、`NOTIFY_RESEND_TIMES`、`MAIL_RETENTION_DAYS`、`SKIP_NON_TRADING_DAY` | 通知的构建/发送/重发时间与保留天数 |
| 定时任务 · 调度器 | `SKIP_NON_TRADING_DAY`、`SCHEDULER_ENABLED`、`SCHEDULER_TIMEZONE`、`SCHEDULER_MISFIRE_GRACE`、`SCHEDULER_COALESCE`、`SCHEDULER_MAX_INSTANCES` | 调度器启停与容错（改时区等会重建调度器） |

> 只改触发时间/间隔 → 原地重注册任务（不中断）；改时区/容错/并发或启停 → 重建调度器。
> 老库启动时会自动补进代码新增的配置项、并清掉已废弃的键（只新增，不动已有值）。

> 调度器与 Web 同进程，因此必须**单 worker** 运行（`run_web.sh` 已固定），避免任务被重复执行。

修改 `WEB_HOST` / `WEB_PORT` / `WEB_LOG_LEVEL` / `WEB_RELOAD` / `SCHEDULER_LOCK_FILE`
需要**重启服务**才生效（设置页备注里已标注），其余配置改完保存即生效。

### 估值区间与信号 / 推荐操作与配色（配置驱动展示）

这两组共 7 个配置项**同时驱动网页和邮件**，改完刷新页面立即生效，不需要重算分位：

| 配置键 | 作用点 |
|---|---|
| `SIGNAL_BANDS` | 五档区间阈值 + 状态名 + 图标 + 长动作文案。决定图表分带与标线位置 |
| `STATUS_STYLE` | 状态 → `[背景色, 文字色]`。用于状态胶囊、图表分带配色、评分数字颜色 |
| `ACTION_SHORT` | 状态 → 短动作词。用于顶部横幅、首页告警表、邮件标题 |
| `ACTION_ICON` | 状态 → 图标。覆盖 `SIGNAL_BANDS` 里自带的 emoji |
| `ALERT_STATUSES` | 哪些状态算"告警"→ 首页告警卡片 + 邮件加 `ALERT_PREFIX` / `ALERT_MARK` |
| `DIVERGENCE_THRESHOLD` | 5 年分位与 10 年分位差超过它 → 网页/邮件提示"短期显著偏离长期" |
| `ALERT_PREFIX` / `ALERT_MARK` | 告警邮件的标题前缀与标记 |

> **为什么改完不用重算分位**：`valuation_score.status/action` 只是**算分位那一刻的快照**，
> 改了 `SIGNAL_BANDS` 之后它就过期了。因此网页和邮件都改用 `config.signal_of()`
> （前端对应 `signalOf()`）按**当前配置 + 评分值**实时推导，两边口径完全一致。
>
> 设置页里这几个编辑器是**互相联动**的：改 `SIGNAL_BANDS` 的状态名，
> `STATUS_STYLE` / `ACTION_SHORT` / `ACTION_ICON` 的键名下拉和 `ALERT_STATUSES`
> 的勾选项会立刻跟着变；每个配置项下方还有一行"适配体检"，缺哪个状态会直接点出来
> （例如 `⚠ ACTION_SHORT 缺少「便宜」`），区间留缝/重叠也会提示。

### 自定义组合（`ktype='portfolio'`）

指数与组合页可以创建自选组合（编码可自定义，留空自动 `pf.001`），
然后搜索个股逐个加入 / 移除。组合与指数走**同一套**评分逻辑：

| 能力 | 说明 |
|---|---|
| 组合编码 | 创建时填写，或自动分配 `pf.NNN` |
| 成分股 | **批量加入**（粘贴代码/名称，换行/逗号/空格分隔，只保留这一个入口）；勾选多只**批量移除**；**等权**，不支持自定义权重 |
| 缺数据的成分股 | 加入时若系统里没有它，**自动去 baostock 拉全量**：K线 + 不复权收盘价 + 分红 + **元数据（名称/行业/上市日期）**；**只补缺的**——元数据齐全的、K线不落后的都不再重复查询 |
| 组合 K 线 | 成分股**等权合成**后写入 `kline`（`ktype='portfolio'`） |
| 指标评分 | 与指数同一套：5 个指标分位 + `valuation_target` 里的评分权重 |
| 成分股变化 | **自动整条重算**：组合K线 → 指标 → 指标分位 → 综合评分 |
| 交互 | 增删后**就地更新成分股列表**（行内增删 + 数量联动），再**后台静默重画横幅与图表**（保留成分股卡片节点与滚动位置，不整页刷新）；移除操作全部是**行内两步确认**（先变红「确认移除？」，再点才执行，3 秒无操作自动还原），不用浏览器弹窗 |
| 重算组合 | 顶部**只保留一个**重算按钮：① 检查成分股 K线/分红/元数据，**只补缺的**（K线落后才补 K线、元数据不全才查元数据）；② 删除旧的组合K线/分位/评分；③ 全量重算并给出综合评分 |

**组合 K 线的价格是"等权收益指数"（基准 1000 点）**，不是成分股价格的等权平均：
后者会被高价股主导（组合里同时有 1500 元的茅台和 9 元的浦发时，涨跌几乎只反映茅台），
等于权重名不副实。做法是「当日收益 = 各成分股涨跌幅的等权平均」再逐日累乘，
这样每只成分股的影响力才真正相等。

> 指数**不改**：指数是"市场的缩影"，继续按**流通市值加权**（`calc_market_weights`）；
> 组合按等权。两者由 `indicators.constituent_weights(ktype, ...)` 统一分派。
> 组合的历史评分同样按"成分股分位等权聚合"（与指数一致，只是权重口径不同）。

### ① `kline` —— K线表（个股 + 指数 + 组合共用）

系统里**最大、最核心**的一张表，一行 = 某标的某交易日的一条 K 线。

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | TEXT | 标的代码，如 `sh.600000`（个股）/ `sh.000300`（指数）/ `pf.001`（组合）。主键之一 |
| `date` | TEXT | 交易日 `YYYY-MM-DD`。主键之一 |
| `ktype` | TEXT | 标的类型：`stock` 个股 / `index` 指数 / `portfolio` 组合 |
| `open` / `high` / `low` / `close` | REAL | 开/高/低/收（**前复权**价，调整行情） |
| `close_raw` | REAL | **不复权**收盘价，只用于计算动态股息率 |
| `preclose` | REAL | 前收盘价 |
| `volume` | REAL | 成交量 |
| `amount` | REAL | 成交额（元） |
| `turn` | REAL | 换手率（%，指数无） |
| `pct_chg` | REAL | 涨跌幅（%） |
| `pe_ttm` | REAL | 滚动市盈率（baostock `peTTM`） |
| `pb_mrq` | REAL | 市净率（baostock `pbMRQ`） |
| `ps_ttm` | REAL | 滚动市销率（baostock `psTTM`） |
| `pcf_ncf_ttm` | REAL | 滚动市现率（baostock `pcfNcfTTM`） |
| `div_yield` | REAL | **动态股息率（%）**：近 12 月每股现金分红 ÷ 当日不复权收盘价 |
| `is_st` | INTEGER | 是否 ST（0/1） |

**三种 `ktype` 的字段含义不同：**

- `stock`（个股）：所有字段来自 baostock；`pe_ttm/pb_mrq/ps_ttm/pcf_ncf_ttm` 是 baostock 直接给的，
  `div_yield` 由「计算指标」任务用 `close_raw` + `dividend` 表算出来写回。
- `index`（指数）：OHLCV 来自 baostock 的指数 K 线；**五个估值字段不是 baostock 给的**，
  而是「计算指标」任务把该指数成分股按流通市值加权聚合后写回本表（本表即指数估值存放处）。
- `portfolio`（组合）：组合没有 baostock K 线，整行（OHLCV + 五指标）都由「计算指标」任务
  按成分股合成后写回。

> 主键为 `(code, date)`。不要再建 `(code,date)` 上的冗余索引（主键已有隐式索引）。
> 现有一个 `idx_kline_type_date(ktype, date)` 辅助按类型+日期筛选。

### ③ `dividend` —— 分红记录（算股息率的依据）

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | TEXT | 个股代码 |
| `ex_date` | TEXT | 除权除息日 `YYYY-MM-DD` |

### ⑧ `valuation_score` —— 分位 / 评分历史（走势图用）

每个标的每个交易日一条。**分位对所有个股/指数都落库；综合评分只有配置了权重的标的才算**
（未配置权重的标的 `score`/`score5` 为 NULL，只存分位）。

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | TEXT | 标的代码 |
| `date` | TEXT | 估值日 `YYYY-MM-DD` |
| `ktype` | TEXT | `index` / `portfolio` / `stock` |
| `score` | REAL | 综合评分（10 年口径，0~100，**越高越贵**）；未配置权重为 NULL |
| `score5` | REAL | 综合评分（5 年口径，参考）；未配置权重为 NULL |
| `pct_pe` / `pct_pb` / `pct_ps` / `pct_pcf` / `pct_dividend` | REAL | 五指标**10 年**分位（已统一方向：越高越贵） |
| `pct5_pe` / … / `pct5_dividend` | REAL | 五指标**5 年**分位（参考口径） |
| `status` | TEXT | 信号状态快照：低估/偏低/正常/偏高/高估（未评分为 NULL） |
| `action` | TEXT | 动作建议快照 |
| `n_used` | INTEGER | 参与计算的成分股数量 |
| `created_at` | TEXT | 创建时间 |

主键 `(code, date)`。

- **个股**：自身指标的滚动窗口分位；**指数/组合**：成分股分位按流通市值加权聚合。
- 分位历史由**手动全量重建**建立（CLI / 首页按钮），日常由「计算指标」任务补。
- **改了权重**不需要重算分位，只需按已存分位重算 `score`（保存权重时自动触发，秒级）。
- 分位口径为**滚动窗口**（10 年 / 5 年），全程无未来数据——历史某天的分位是该天用截至
  当天的数据算出的，不会被后续行情改写。
- 前端评分走势图、五指标分位图都读这张表。

### 首页接口性能（部署到树莓派后尤其重要）

首页 `/api/dashboard` 曾要 **~3.2s（本机）/ 20~32s（树莓派）**，瓶颈全在三个
"全表统计"查询上 —— 而首页每 30 秒自动刷新一次，等于拿最贵的查询喂最高频的刷新。

| 查询 | 本机 | 问题 |
|---|---|---|
| `count_stocks` | 359ms | `COUNT(DISTINCT code) FROM kline`，扫 316 万行 |
| `latest_kline_dates` | 767ms | `GROUP BY code`，扫 316 万行 |
| `latest_score_dates` | 768ms | `GROUP BY code`，扫 262 万行，**还被调了两次** |
| `config.target()` × 856 | 525ms | 每次调用都 `_connect()` 重开连接 + 整表读 |

**三处优化：**

1. **`_alert` 只遍历「标的信息」里的标的**（`_alert` 原来遍历全部 860 个代码）：
   只有标的有 `score`，其余 260 万行 `score` 为空、只落分位 —— 那些代码
   `signal_of(None)` 恒为「未知/非告警」，纯属白跑。实测 **1262ms → 1.1ms**。
2. **首页统计加进程内短缓存**（`WEB_STATS_CACHE_SEC`，默认 60 秒）：
   key 里带 `data_fingerprint`（取数任务写过库就**立即失效**），TTL 兜住计算任务写的
   变化（评分/分位，指纹反映不出来）。实测 **1848ms → 0.7ms**（命中）。
3. **`config.target(code)` 改走主键直查**（原来是遍历整表）。

> 端到端：`/api/dashboard` **冷 1947ms → 命中 ~5ms**（约 390 倍）；
> 树莓派上约 **11s → 0.03s**。缓存可关（`WEB_STATS_CACHE_SEC=0`）。

**顺便实测否掉的两个"想当然"方案**（避免以后走弯路）：

* **给 `kline` 加 `(code,date)` 索引** —— 实测 `latest_kline_dates` **没变快**（781ms）、
  `count_stocks` 反而更慢，还要花几秒建索引 + 占磁盘。**别加**。
* **`config.target` 改成主键查的独立收益很小** —— 860 次调用的 400ms 里绝大部分是
  **每次 `_connect()` 的开销**（表里只有 5 行，扫不扫无所谓）。
  所以"少调用"比"改查询"重要得多：真正的解法是第 1 条（不再逐只循环）。

### 指数分位口径：用「聚合值自身的历史分位」，不是「成分股分位的平均」

这两者在数学上**不是一回事**：「平均的分位」≠「分位」。

* 旧做法：把 300 只成分股各自的历史分位**加权平均**（`index_score` 里逐只累加）；
* 现做法：先算出指数聚合值（总市值/总盈利…），再看**这个值**落在自身历史的什么位置。

主流口径（雪球等）用的是后者。实测两者能差 20+ 个分位点（沪深300，2026-09-11）：

| 指标 | 当前值 | 旧：成分股分位加权平均 | 新：聚合值自身分位 |
|---|---|---|---|
| PE | 13.41 | 46.4% | **62.9%** |
| PB | 1.51 | 48.4% | 48.3% |
| PS | 1.46 | 53.4% | **78.0%** |
| PCF | 9.66 | 51.9% | **27.3%** |
| 股息率 | 2.67 | 42.7% | **31.9%** |

**而且实现更简单更快**：`rebuild_index_valuation` 早就把聚合后的估值写进了指数自己的
`kline` 行，所以直接对它算滚动分位即可 —— 和个股用的是**同一个**
`stock_metric_percentiles`，不必再遍历几百只成分股（实测 **6~9s → 59ms**）。
历史序列（`rebuild_score_history`）也走同一条路径，否则走势图和当日评分会打架。

> **分位方向**：本系统的分位一律是**「贵度分位」**（越高越贵）。
> 股息率是反向指标，由 `INVERTED = {"div_yield"}` 处理 —— 股息率越高 → 贵度分位越低
> → 越便宜。所以 `pct_dividend = 31.9%` 说的是"便宜度约 68%"。

> **PCF 的口径局限**：baostock 的 `pcfNcfTTM` 分母是**现金净流量**（含投资/筹资活动，
> 常为负），而雪球用的是**经营活动现金流**。实测沪深300 有 **123/300 只成分股 PCF 为负**
> （被 `_valid` 剔除），剩下的 171 只跨度 0.49~943，所以这个值**和雪球不可直接比较**。
> 要对齐需要另取现金流量表数据，属于独立改造。

### 无效的 0 值（比率型指标）

baostock 对停牌/无数据的标的会给 `peTTM`/`pcfNcfTTM` 等填 **0**，而比率型指标的 0 是
非法值（`VALID_RANGE` 下限 0.01）。这些 0 会被分位计算里的 `_valid` 剔除，但**显示没有兜底**
—— 会被当成"绝对值 0"显示、画进估值图。

修法：`rebuild_index_valuation` 写回时用 `_valid` 过滤（不只过滤 None），并清理存量
（实测清掉 PE 27.8 万行 / PB 1.6 万 / PS 1 万 / **PCF 136.5 万行**）。
`div_yield` 的 0 **不清** —— 无分红是有效观测（`VALID_RANGE` 下限给的是负数）。

### 「计算指标」任务：分阶段 + 并发

每 30 分钟跑一次，所以**检查必须便宜、重活必须只做一次**。阶段之间有依赖，顺序不能换：

| 阶段 | 做什么 | 并发 |
|---|---|---|
| ⓪ 数据变化闸门 | 取数侧没写过东西 → **直接早退**（0.3ms） | — |
| ① 补股息率 | 个股动态股息率，只补"有 close_raw 且为空"的 | — |
| ② **个股分位** | 只处理**历史残缺 / 被标脏**的（整条重建） | ✅ 多进程 |
| ③ **组合 K 线落库** | 组合的分位要靠它当日期轴；**按需重建**（输入没变就跳过） | — |
| ④ **指数 / 组合聚合** | 读 ② 已落库的个股分位加权，不重算 | ✅ 多进程 |
| ⑤ 兜底补最新 | 所有标的的最新交易日，已经是最新的直接跳过 | — |

**⓪ 数据变化闸门（为什么需要）**：任务每 30 分钟跑一次，但数据只在 `data_sync`
（20:00）之后才变，所以一天里绝大多数轮次是**空转**。闸门用
`MAX(updated_at) FROM sync_state`（0.3ms）当"数据指纹"：

* 指纹**只认取数侧写的 dtype**（白名单 `kline/dividend/constituent/close_raw/
  trade_date/kline_full`）—— 用黑名单踩过坑：计算任务自己写 `pf_fp`/`pct_history`
  也会改指纹，闸门永远关不上；
* 只有在"这一轮**确实没留下待办**"（`lagging == 0` 且没有 dirty 标的）时才记指纹，
  否则下一轮必须继续做，不会把没补完的缺口一起跳过；
* **手动点「执行」会绕过闸门**（`force`）—— 手动触发就是要真跑一次。

**③ 组合 K 线按需重建**：以前无条件全量重建，2843+1735 行 × 48 次 ≈ **22 万行/天**
写入（树莓派 SD 卡上的真实磨损）。现在只有"组合 K 线没到最新交易日"**或**
"数据指纹变了"才重建。

> 实测：第一次 144.5s（含一次性追平），**第二次 0.0s 直接早退**；
> `force` 时组合重建 `portfolio_skipped=2 / portfolio_rows=0`（跳过）。

**怎么判断"分位缺失"**：不是看「分位字段 IS NULL」——早期交易日的窗口长度不够，
分位**天然算不出来**（永远是 NULL），拿它当缺失会让每轮任务重试几十万天、永远补不上。
所以用三个判据：

1. **`pct_dirty` 标记**（输入数据变了 → 无条件重建）：见下面「派生失效」一节；
2. **覆盖率**：`评分行数 / K线行数 < 0.9` → 判为历史残缺（例如刚进个股池、
   只在最新一天算过一次的股票）；
3. **水位**：补过的在 `sync_state` 打 `pct_history` 标记（`dtype='pct_history'`），
   之后只补最新交易日，不再整条重建。

#### 派生失效：取数改了输入，计算必须重算派生历史

这是两个任务交界处**最容易掉的一环**：`data_sync` 改了原始数据（K 线 / `close_raw` /
`div_yield`），派生出来的**历史分位序列**就作废了，但覆盖率判据**看不出来**
（K 线行数没变），水位标记还会主动跳过它。

所以由**改数据的那一方显式打标记**：`fill_dividend_yields` 发现某只股票的股息率
发生**历史性变化**（最早改动日期早于 `最新交易日 - 30 天`，即不是日常增量重写的那
最近几天）时，调用 `storage.mark_history_dirty()` 打上 `pct_dirty`，下次
「计算指标」就会无条件重建它的整条历史分位，重建完自动清标记。

> 为什么阈值是 30 天：日常增量只重写最近 `KLINE_OVERLAP_DAYS`(10) 天，
> 那种变化由"补最新一天"覆盖，没必要为它整条重建；只有真的动到历史
> （`sync_kline(full=True)` 全量重拉、`close_raw` 补齐）才重建。

> 实测：`sh.600004` 覆盖率 **99.7%**（≥90%）且无 `pct_history` 标记 ——
> 光靠覆盖率判据**完全发现不了**它；靠 dirty 标记救回来后，
> `pct_dividend` 从 **249/5660（4.4%）→ 5660/5660（100%）**。
> 全库一次端到端：补股息率 **2,199,737 行**，触发 **589 只**历史重建
> （252 万行），个股 `pct_dividend` 非空从 **29 万 → 265.8 万**；第二次运行 11.6s 无重活。

> 实测（838 只个股 / 3 指数 / 2 组合）：首轮识别出 **115 只个股 + 2 个组合**残缺，
> 补齐 **70.7 万行**，耗时 ≈76s（个股重建只要 0.2~0.5s/只，组合 ≈16s）；
> 第二轮起重活全部跳过，≈34s。仍然 `<90%` 的只有 3 只**新上市**股票
> （上市不足一个月，前期达不到最小样本数），已打标记不再重试。

**并发度**取 `REBUILD_WORKERS`（0=自动 = `min(3, 核数-1)`；树莓派 3B+ 4 核 → 3 进程，
留 1 核给 web/调度器）。单线程进程用 `fork`、web 后台线程用 `spawn`
（避免 fork 继承到别的线程持有的锁而死锁）。

**指数聚合的复用优化**：`index_score` 原先对**每只成分股从 kline 原始数据重算分位**
（300 只 × 10 年窗口排序），而库里其实已经存好了该股的分位。现在优先读已存分位
（`_stored_pcts_asof`），读不到才回退重算 —— 实测指数全历史聚合 47s → 16.5s，
日常单日聚合也从 6~9s 降到 1s 内。

**指数估值聚合的缺失判据只看 `pe_ttm`**（不看 `div_yield`）。原因：个股的 `div_yield`
要先有 `close_raw`（不复权收盘价）才能算，而库里绝大多数个股没有 `close_raw`
（实测只有 49/838 只），那些历史日期的 `div_yield` **永远算不出来**。以前把它当"缺失"
会导致每轮重算上千天（sh.000300 1214 天 / sh.000905 1104 天，每 30 分钟白跑 ~25s）。
现在只重算「`pe_ttm` 为空的新日期 + 最近 5 个交易日」（后者是为了覆盖修正盘中的快照），
实测 **1214 天 → 5 天，11s → 0.03s**。历史 `div_yield` 的补齐要靠全量重建
（`only_missing=False`），前提是先补上成分股的 `close_raw`。

## 数据与计算流程

### 1. 拉取数据（纯取数）

`data_fetcher.sync_all`：

1. 交易日历 → `trade_date`
2. 上证指数 K 线 → `kline`（`index`，仅行情展示）
3. 成分股 → `index_constituent` + `stock_basic`
4. 标的元信息 → `stock_basic`（名称/类型/市场，并**批量补全行业 + 上市日期**）
5. 指数 K 线（前复权） → `kline`（`index`）
6. 个股 K 线（前复权） → `kline`（`stock`）；不复权收盘价 → `kline.close_raw`
7. 分红 → `dividend`
8. 出现新分红 → 全量重拉该股前复权 K 线（修正历史）并重拉不复权价

> 行业/上市日期用 `query_stock_industry` 与 `query_stock_basic` 各**一次批量查询**补全，
> 只定点 UPDATE 这两个字段（不覆盖已有名称/类型/市场）。也可单独跑：
> `.venv/bin/python -m src.fetch_data.data_fetcher --only basic`

### 2. 计算指标（纯离线）

`indicators.compute_all`（每 30 分钟，增量）：

1. **补股息率**：找出 `div_yield` 为空的个股，用 `close_raw` + `dividend` 算出来写回 `kline`
   （**没有分红记录的按 0 处理**）
2. **指数估值聚合**：缺失日期 → 按成分股流通市值加权聚合五指标写回 `kline` 指数行
3. **组合 K 线合成**：缺失 → 按成分股合成 OHLCV + 五指标写回 `kline` 组合行
4. **综合评分**：对有权重的指数/组合/个股，算当日评分写回 `valuation_score`
5. **分位补最新**：给所有个股/指数补最新一天的分位（缺才补）

### 2.1 全量重建（手动，首次/补历史）

`indicators.rebuild_all_percentiles`（CLI / 首页按钮）：

1. **个股/组合**：多进程并行，各自「全量重算动态股息率（无分红置 0）+ 重建分位历史」
2. **指数**：读成分股**已存分位**按流通市值加权聚合（不重算）

> 性能：分位计算早期用 `bisect.insort`（O(n²)），8000 行的个股要 2.5s；
> 窗口起点预计算后降到 ~0.15s（16 倍），再叠加多进程并行。

### 3. 评分算法（简述）

- **权重**：流通市值 = 前复权收盘价 × (成交量 ÷ (换手率/100))
- **指数估值聚合**：PE/PB/PS/PCF 用调和加权 `Σw/Σ(w/x)`；股息率用算术加权 `Σ(w·x)`
- **分位**：每个指标对自身历史做滚动窗口（10 年/5 年）线性排名分位，统一为"越高越贵"（股息率取 100−p）
- **合成**：`score = Σ(w·pct) / Σw`，缺失指标自动剔除并归一；**未配置权重只存分位、不算 score**
